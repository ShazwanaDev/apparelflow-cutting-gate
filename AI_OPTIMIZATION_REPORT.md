## 2. Flawed or Broken AI-Generated Code

The examples below are actual issues documented during development, not hypothetical weaknesses. Some were exposed by automated tests or browser checks, while others came from reviewing the application and its behavior. I used those findings to direct corrections instead of accepting the generated output unchanged.

### 2.1 Missing verifier attribution in the sewing queue

The first sewing-queue implementation joined an approval record through a SQL `LATERAL` subquery, but it reused a shared `SELECT` list that did not include the verifier's name, approval timestamp or approved wastage. As a result, a verified batch could reach the sewing interface with `verifierName: undefined`. The TypeScript row shape had been asserted, so the missing fields were not caught by type checking.

**How it surfaced:** An automated test checking verification attribution exposed the problem.  
**Correction I required:** Ensure the sewing query explicitly selects the approval fields and verify the API response, not just the internal query result. The generated change separated `SUMMARY_COLUMNS` from `SUMMARY_FROM` and selected the additional approval columns. The fix is recorded in `203a269`, with regression coverage in `79d8c41`.

This mattered because a handoff without verifier attribution undermines the traceability that the assessment explicitly requires.

### 2.2 Invalid dummy password hash in authentication

The generated sign-in route attempted to reduce email-enumeration timing differences by comparing an unknown user's password against a dummy bcrypt hash. However, the proposed hash was an invented bcrypt-looking string rather than a valid generated hash. That could make unknown-account requests return early, defeating the intended timing protection.

**How it surfaced:** The issue was identified during code review before that version was committed.  
**Correction:** Replace the placeholder with a real bcrypt value created using `bcrypt.hashSync('no-account-has-this-password', 10)` during startup, and cover the failure-response behavior with a test.

The lesson I took from this was that a convincing security comment does not prove that the code beneath it is secure.

### 2.3 Pipeline stepper did not show the current stage

The CUTTING / VERIFICATION / SEWING progress stepper failed to highlight its current stage. A role-to-stage lookup was exported from a module marked `'use client'` and imported into a server-rendered component. The server did not receive the normal constant value, so the lookup returned `undefined` without a useful type or runtime error.

**How it surfaced:** Browser screenshot review revealed the missing active state; a subsequent check found no `aria-current="step"` element.  
**Correction:** Move the shared stage constants into a normal module, `lib/stages.ts`, that can safely be imported by server and client components (`d1922b4`).

### 2.4 Reduced-motion hydration mismatch

AI-generated entrance animations used `initial={reduce ? false : { opacity: 0, y: 8 }}`. The server could not know the user's reduced-motion preference, producing different initial markup and client-side rendering. In the affected case, React reported a hydration mismatch and hidden initial styles could remain.

**How it surfaced:** Playwright was used to emulate `prefers-reduced-motion: reduce` and inspect console output.  
**Correction:** Use matching initial styles for server and client rendering, with Motion's `reducedMotion="user"` behavior controlling movement later (`d1922b4`).

### 2.5 Additional defects and refinements

- **Database transaction queries:** AI-generated `Promise.all` calls attempted concurrent queries on one transaction client. A real PostgreSQL run exposed a driver warning that the in-memory test database had not surfaced. The code was changed to execute the transaction queries sequentially (`83690cc`).
- **Driver portability:** An array parameter using `ANY($1::order_status[])` worked in node-postgres but failed in PGlite, causing transition tests to return `500`. The test failures led to a compatible query change.
- **Order-list alignment:** **I personally noticed** that status badges of different lengths were shifting columns between rows. I requested a stable column layout rather than leaving each row to size itself independently (`ee531c6`).
- **Role-switcher placement:** **I personally questioned and changed the placement** of the role switcher when it made the header crowded. I directed its move to a side dock to keep the main header readable and consistent.

## 3. Human Review, Refactoring and Optimization

My approach was to **own the problem and the result, while using the AI tools to type the implementation**. When I found a design, security or usability concern, I explained what was wrong, defined the expected outcome, asked for a specific change and reviewed the result. I did not claim authorship of the generated lines of code; my contribution was the judgment and direction behind those revisions.

### 3.1 Challenging the security of the demo role switcher

I raised a question about whether switching factory roles inside an existing session could create a security loophole. The reviewed flow signs the current user out and signs in as another demo account; it does not change a role field inside a trusted session. The backend reads that account's role from the database on each request.

I also considered the risk of exposing demo credentials. The resulting `NEXT_PUBLIC_DEMO_MODE=false` configuration hides the demo switcher and credential cards in a non-demo build. This means the demonstration experience is not treated as a production authentication design. I required the API's role enforcement to remain independent of what the role switcher displays.

### 3.2 Making layout feedback actionable

I assessed the generated interface as a working product, not just a collection of attractive screens. Two changes came directly from my review:

- Moving the role switcher from the crowded header to a side dock, preserving a clean single-row header.
- Fixing order-list columns whose positions varied with the width of each status badge.

These were human-identified usability problems, even though Claude generated the CSS and component changes that resolved them.

### 3.3 Strengthening server validation

I required the server to reject unexpected request fields instead of silently ignoring them. For example, an approval payload attempting to supply `verifier_id`, `status`, or `expected_qty` must receive `422` rather than being partially accepted. Likewise, component counts must be genuine JSON numbers: numeric strings such as `"12"` are not accepted through automatic coercion.

This makes tampering visible and prevents permissive parsing from changing what a request means. The code implementing these checks was AI-generated, but the safeguard and its acceptance criteria were part of the engineering review I directed.

### 3.4 Keeping the database, UI and calculations consistent

I required the traffic-light flag to reflect the stored expected and actual counts, not a client-supplied color. The final design uses a generated PostgreSQL column so GREEN, YELLOW and RED cannot disagree with the underlying quantities.

I also required stable fabric-wastage calculations. The implementation works in whole hundredths of a yard where appropriate, instead of relying on floating-point operations such as `1.1 * 120`, which can produce `132.00000000000003` in JavaScript.

My priority in both cases was to avoid subtle discrepancies between what the UI displays, what the server approves and what the database records.

### 3.5 My acceptance standard

I did not regard generated code, passing TypeScript checks, or a polished interface as sufficient on their own. I assessed whether the implementation met the original business rules: unauthorized users must be blocked at the API, shortages must never pass approval, pending batches must remain hidden from sewing queries, audit details must survive handoff, and data must persist after reloads. I used test failures, browser observations and security-check outputs to guide further correction requests.

**In short: Codex and Claude wrote the code. I interpreted the problem, set the requirements, directed the work, questioned the outputs, raised corrections and took responsibility for the resulting engineering decisions.**

## 4. Defensive Architecture and API Guards

The final architecture was designed around the principle that **the server and database must enforce every critical manufacturing rule**, even when someone bypasses the interface and sends requests directly.

### 4.1 Centralized domain validation

Route handlers read the authenticated session and pass requests into the domain service layer in `lib/domain/orders.ts`. The service checks the user's role, validates the body and enforces the operation's business rules. Server-rendered pages use the same domain functions, avoiding a separate, weaker path for UI requests.

The intended failure categories are explicit: `401` for missing authentication, `403` for a forbidden role or request, `422` for invalid input, `404` for an inaccessible or missing resource, `409` for an invalid or conflicting transition, and `422` for a batch that fails the hard-stop quantity check.

### 4.2 Explicit state machine and hard-stop gate

Allowed movements between the cutting, pending-verification, verified and sewing states are defined in `lib/domain/state-machine.ts`. A client cannot send an arbitrary status override through a generic update endpoint.

For a verification transition, the service:

1. Starts a database transaction and locks the relevant order row using `SELECT ... FOR UPDATE`.
2. Checks that the role and current state permit the requested action.
3. Re-reads component counts from the database rather than trusting numbers or traffic-light flags supplied by the browser.
4. Blocks approval with `422` if any required count is missing, uncounted or below the expected quantity; the transaction does not partially approve the batch.
5. Writes the approval or rejection record and timeline event as part of the controlled transaction.
6. Applies a conditional state change so concurrent requests cannot both approve the same transition.

This enforces the physical factory rule: **no unverified or shortage batch enters sewing**.

### 4.3 Session-derived identity and RBAC

Authentication uses an HS256-signed JWT held in an `httpOnly`, `SameSite=Lax` cookie. The token identifies the user; the server retrieves the active role from the database. Verifier attribution comes from that trusted identity, while database timestamps are generated by PostgreSQL's `now()`.

The cutting supervisor cannot approve a batch, the verifier cannot create cutting orders, and the sewing supervisor cannot access unverified work merely by changing a URL or sending a direct API request.

### 4.4 Sewing-queue isolation

Sewing queries apply a database-level status filter: `WHERE o.status IN ('VERIFIED', 'IN_SEWING')`. The displayed tab can further narrow that permitted set, but cannot widen it. Single-batch access uses the same eligibility restriction, so an unverified batch ID returns `404` instead of exposing its record.

### 4.5 Database constraints and immutable audit records

PostgreSQL enums and constraints reject invalid values, including impossible quantities and incomplete audit states. Examples include `target_qty > 0`, `actual_qty >= 0`, required verification timestamps for verified orders, and a sufficiently detailed rejection note. Generated status flags depend on count values rather than user-controlled inputs.

Audit tables such as `verification_logs` and `order_events` are append-only. Database triggers prevent UPDATE, DELETE and TRUNCATE, and SQL-level tests exercise these restrictions. This ensures that the verifier's identity, decision, quantities, wastage and time of approval remain traceable after handoff.

### 4.6 Testing and final verification

The documented test suite contains **100 Vitest tests** using PGlite, an in-memory PostgreSQL-compatible database. The recorded production-build cURL checks cover missing sessions (`401`), role violations (`403`), shortage approvals and malformed input (`422`), attempts to access pending sewing batches (`404`), repeated approval (`409`) and cross-site requests (`403`). Browser checks also covered multiple screen widths, keyboard navigation and reduced-motion behavior.

Claude generated much of the test code and the automated tools executed scripted checks. **My responsibility was to choose the important cases, examine the results, identify unacceptable behavior and direct fixes.** That distinction is the central point of how I used AI in this assessment: I treated code generation as an implementation aid, not as a substitute for engineering judgment.
